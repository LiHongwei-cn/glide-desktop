# Glide 专业操作与发布规范

## 1. 连接资料生命周期

### 1.1 导入前

1. 线路名称保持唯一、可识别，最多 64 个字符。
2. 管理入口必须是公开域名的 HTTPS 地址，并明确指向 `/admin`。
3. 地址不得包含用户名、密码、查询参数或片段。
4. 同一管理入口只允许导入一次。
5. 管理密码只在当前表单内短暂存在，不进入日志、诊断或工作区数据库。

### 1.2 只读检查

1. 前端先做格式、长度和重复检查。
2. 桌面端重新解析地址并执行 DNS 检查。
3. DNS 结果包含本机、私网、保留、文档或地址转换网段时立即停止。
4. HTTP 重定向不自动跟随，避免跳转到未验证目标。
5. `401`、`403`、`405` 表示入口可达且受到保护；`404` 和其他异常状态只算有限通过。

### 1.3 保存

1. 通过只读检查后才显示最终确认页。
2. 管理密码写入 macOS Keychain 或 Windows Credential Manager。
3. 工作区只保存随机凭据引用和脱敏地址标签。
4. 新线路初始为“待验证”，首次诊断后才更新健康状态。

### 1.4 删除

1. 删除操作必须再次确认。
2. 先删除系统凭据，再删除本机线路记录。
3. 系统凭据删除失败时保留线路记录并提示重试。
4. 本机删除不会修改远端服务器；远端泄露仍需服务端轮换。

## 2. 诊断与健康度

1. 相同管理入口在一次诊断中只检查一次。
2. 每批最多检查 20 个入口，单次最多 100 个，避免误触发流量或风控。
3. 诊断结果只保存脱敏入口、状态、耗时和可操作说明。
4. 健康度只表示管理入口的近期可达性，不代表出口国家、吞吐量或长期稳定性。
5. 国家地区必须由至少两个独立证据源一致确认后，才能标记为“已验证”。
6. 深度吞吐测试必须由用户主动触发，不能后台静默运行。

## 3. 订阅与设备分享

1. 订阅必须使用公开域名的 HTTPS 地址。
2. 每台设备使用独立订阅凭据和清晰名称。
3. 订阅原文只保存在系统凭据库，二维码只在当前窗口短暂显示。
4. 剪贴板可能被系统同步或历史工具读取；导入后应立即清空。
5. 删除 Glide 本机记录不等于撤销服务端订阅。

## 4. 客户端下载

1. 只打开项目维护者的官方 GitHub Releases 页面。
2. 用户必须按操作系统和 CPU 架构选择安装包。
3. 正式分发必须提供签名、SHA-256 和发布说明。
4. 未签名 Windows 包只作为 CI 测试工件，不面向普通用户发布。
5. 未完成 Apple Developer ID 签名和公证的 macOS 包必须标记为预览版。

## 5. 本地隐私边界

允许保存在本机工作区：

- 线路显示名称和配置地区
- 管理入口完整地址
- 随机凭据引用
- 脱敏诊断结果
- 本机启动次数和活跃日期

禁止进入工作区、日志和遥测：

- 管理密码
- 订阅原文
- API Key、Token 和全局密钥
- 用户浏览历史
- 可跨设备识别用户的持久标识

## 6. GitHub 发布闸门

每次发布前必须全部满足：

- 前端测试、覆盖率、生产构建通过
- Rust 测试、格式和严格 Clippy 通过
- 生产依赖审计无高危漏洞
- 源码敏感信息扫描无命中
- macOS 与 Windows CI 构建通过
- Release 附带 SHA-256 校验文件
- Release 明确平台、架构、签名和已知限制
- Secret Scanning、Push Protection、Dependabot 安全更新保持启用

## 7. 参考实现

流程设计参考了以下成熟开源项目的公开做法，但 Glide 不复制其代理核心：

- [Hiddify App](https://github.com/hiddify/hiddify-app)：重复配置防护、配置验证、HTTPS 订阅和设备端体验
- [Clash Verge Rev](https://github.com/clash-verge-rev/clash-verge-rev)：备份恢复、错误可操作化、桌面权限与跨平台发布
- [Tauri](https://github.com/tauri-apps/tauri)：能力白名单、CSP、签名和桌面 IPC 安全边界
